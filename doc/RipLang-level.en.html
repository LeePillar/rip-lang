    Rip Language Development Specification v1.3

    This document is the complete specification for compiler implementers. Rip is a strongly typed, zero-inference, class-free server/Web language with reference counting plus cycle collection and Rust ownership semantics; its file suffix is .rp, its tool is rip, and its package manifest is rip.toml. Core principle: exactly one way. One semantics allows exactly one syntax; aliases, sugar, and second spellings are forbidden (except the convenience sugar explicitly listed in this specification). Implementation goal: dual mode of interpreter + AOT compiler, hosted on Rust. Authority boundary (mandatory): the deliverables of this repository are the Rip runtime and toolchain implemented in Rust (compiled artifacts or Rust source). Rip is a general-purpose language for everyone, not an internal scripting language for any single project. demo/ holds only verification examples written in Rip; examples are subordinate to the language specification, and the language specification is not subordinate to examples — any change to lexing, grammar, types, ownership, or standard library semantics made merely to get some demo working is prohibited.

    0.2 Two Execution Modes

    ModeCommandDependency
    Direct source executionrip run, rip devThe target machine must have the rip runtime installed
    Native binary (AOT)rip buildThe artifact is a native executable; the target machine needs no runtime installed and it contains no Rip source
    • Source execution is used for development and operational hot updates; native binaries are used for delivery and deployment.
    • rip build performs full AOT by default: it translates all Rip syntax into a host program, links the runtime library distributed with rip, and then has the built-in compiler component generate a native binary.
    • --aot is retained for compatibility with old scripts and behaves the same as the default.
    • Both modes must be semantically identical: the same source has the same behavior, diagnostics, and exit codes under run and build; rip test --diff <dir> compares them file by file automatically.
    • The former single-file artifact of "interpreter + embedded source" has been removed: it is neither more convenient than source execution nor lighter than a native binary, an intermediate state that wins on neither end.

    Execution model: the runtime consists of a "bytecode fast path + tree-walking interpreter".

    • Pure scalar functions (local variables, arithmetic/comparison/logic, if/for, function calls, module and method calls) are compiled into stack bytecode, with variables accessed by slot instead of by name hash lookup.
    • Functions containing structs, vec/map, match, closures, globals, or ? fall back to the interpreter as a whole; both paths share the same operation, call, and error semantics, and the #[test] and demo/server regression cases must produce identical output on both.
    • Bytecode compile-time optimizations: literal constant folding, scope-based slot reclamation and reuse, int -specific slot instructions (slot op constant, in-place slot update, conditional direct jump), hot expression fusion ((x op constant) op y, expression % constant written back directly), and direct indexed calls to compiled functions; overflow, division by zero, and type mismatch still fall back to the unified implementation with the same errors.
    • Bytecode is compiled only once: the result is shared via RuntimeSeed together with Arc, so HTTP worker threads, parallel branches, task.spawn, and parallel tests that each create a new runtime no longer recompile; strings in instructions also use Arc, so the compiled artifact can be reused across threads.
    • Memory model: containers are Rc<RefCell<…>> and are freed immediately when acyclic; cycles such as "container → closure → captured container" are located by the in-thread cycle collector using trial deletion to find objects with no external references and are then cleared (triggered automatically at allocation intervals at request/test end, or manually with sys.gc()). sys.heap_usage() returns heap usage as counted by the counting allocator; [server] max_heap_mb sets the process heap limit; when exceeded, collection runs first, and if it is still exceeded the current request fails.
    • Troubleshooting switch: setting RIP_NO_VM=1 disables the bytecode path entirely and forces the interpreter for behavior comparison.

    Experimental native compilation (rip build --native):

    • Translates the "scalar int subset" into a host program and then invokes the built-in compiler component to produce a native executable; intermediate sources are written only to the current project root's .tmp/ and deleted when compilation finishes (the directory is removed too if it becomes empty), so they never appear in the delivery directory.
    • Supported scope: int/void parameters and return values, local int variables, arithmetic/comparison/logic, if/else, both forms of for, return/break/continue, direct function calls (including recursion), string literals and + concatenation, int.to_string(), print (a single int/string), and int constants.
    • Out of scope (structs, vec/map, match, closures, module calls, db/http, mutable globals, etc.) produces an explicit error suggesting rip build instead, and never generates an artifact with inconsistent semantics.
    • This path is still experimental and suits compute-intensive tasks and performance verification; business applications (database, HTTP) should use the full AOT of rip build.

    Full AOT (rip build default):

    • Translates all Rip syntax into a host program (value model, operations, and calls uniformly use the runtime Value), links the host support library, and then produces a native binary with the built-in compiler component; the interpreter is not involved and Rip source is not embedded.
    • Coverage: functions/recursion, closures and captures, struct/vec/map, match (some/none/ok/err/structs), loop/while/while let/for-in, ?, modules and third-party packages, and all of std/*.
    • Native scheduling: the generated binary carries a function table, an annotation route table (#[get] etc.), and an #[interval] timer table; HTTP worker threads, task.spawn, and ws.serve are rebuilt by name with behavior identical to interpreted mode; rip.toml 's [runtime], [server], and [cluster] are written into the artifact at build time.
    • Command line: the generated binary accepts --port / --host / --cert / --key, the same as rip run.
    • Build dependencies: the user's machine does not need any compilation tools installed; the compiler component, linker, and runtime library ship with rip (see 10.11). On Windows, MinGW targets use the toolchain's bundled rust-lld, and MSVC targets use the system link.exe.
    • Clean artifact: links rp-core by default (the interp build with the rp-runtime feature disabled), so the artifact contains neither an AST interpreter nor a bytecode VM; if rp-core cannot be found, it falls back to linking rp-runtime and prints a notice. See 10.9 for how to build.
    • Difference from --native: --native covers only the scalar int subset and produces a fully independent artifact; rip build covers the whole language, but the artifact still links the host support library (already statically linked into the binary).

    0.3 Example (demo/) boundaries

    demo/ is a consumer of the language and toolchain, not its definer:

    1. Examples may use only capabilities already defined by the current specification; anything missing must first go through language evolution, and special cases must not be invented inside examples.
    2. Examples must not add keywords, aliases, implicit conversions, or syntactic sugar for their own sake, nor relax type/ownership checks.
    3. Examples must not add runtime special-casing that applies "only to a certain directory / a certain file name".
    4. When examples reveal a flaw in the specification, the order is: fix this specification first → then fix the implementation and tests → fix the examples last, with a record kept for all three steps.
    5. Example code must not become the de facto standard for standard library semantics; standard library behavior is governed by Section 11.
    6. demo may freely choose its directory organization and naming, but it must not in turn require changes to Section 10 of this specification or to the project directory structure conventions in demo/README.md.

    2.1 Identifiers

    Keywords cannot be used as variable, function, type, or module names. The only exception: a member name after . may share a keyword's name (the standard library already has http.static); it is treated as a member name, and this may not be extended to other positions.

    package and import have been removed from the language: they are not keywords, no corresponding declarations exist, and writing them in source only produces a syntax error with no compatibility path.

    Quote rules:

    • "..." is a string of any length and supports the escapes \n \t \" \\.

    • """...""" is a multiline template: line breaks and indentation are preserved as-is, and ${expression} inside the content is evaluated and then concatenated; \${ denotes a literal ${.

    Interpolation is expanded into ordinary string concatenation at parse time ("a" + x.to_string() + "b"), so source execution and native compilation behave identically.

    • Ordinary double-quoted strings do not interpolate and keep their original semantics.

    2.6 Attributes (Annotations)

    Attributes are language-level metadata, not comments:

    #[name]
#[name("string", "string")]

    Rules:

    • They may only be written before a module-level func declaration; a function may have several attributes, each on its own line.
    • An attribute name is an identifier; arguments may only be one or more double-quoted strings.
    • Attributes are parsed into the AST at compile time; they do not participate in runtime evaluation and cannot be used as ordinary expressions.
    • An attribute name must belong to the set defined by the standard library; an undefined attribute name is a compile error.
      • HTTP routing: #[get(...)], #[post(...)], #[put(...)], #[delete(...)], #[patch(...)], #[options(...)], #[head(...)]. See 11.2.1 for semantics.
      • Background tasks: #[interval("1s")]; time units support ms, s, m, h.
      • Testing: #[test].
    • A route attribute must have exactly one string argument, and the path must begin with /.
    • #[test] takes no arguments; the tested function must have no parameters and its return type must be void. The function body asserts with dev.assert and is executed by rip test (see 10.7).

    3. Type System

    3.1 Integers and Floating Point (Rust semantics)

    TypeDescription
    intSigned 64-bit, equivalent to i64, the default integer type
    float64-bit floating point, equivalent to f64, the default float type
    i8 / i16 / i32 / i64Fixed-width signed integer
    u8 / u16 / u32 / u64Fixed-width unsigned integer

    Rules:

    • Radix uses a prefix (0x / 0o / 0b), the type uses a suffix (42i32, 7u8); an integer without a suffix is int.
    • int2 / int8 / int16 are no longer types, and a literal prefix no longer determines the type either.
    • Different integer types have no implicit conversion; mixing them is a compile error; operations on the same type are computed at that type's width, with overflow panicking (no wrapping), and the error is reported at the operation — intermediate results are checked too, rather than being caught only at assignment.
    • When initializing from a literal, the suffix type must be able to hold the value (256u8 is a compile error).
    let a: int = 42;          // int = i64
let b: u8 = 0xFF;         // the prefix only gives the radix
let d: i32 = 42i32;     // explicit suffix
let g: u8 = a.to_u8();    // truncated

    Methods: .to_int(base) (= .to_i64(base)) / .to_i8(base) / .to_i16(base) / .to_i32(base) / .to_i64(base) / .to_u8(base) / .to_u16(base) / .to_u32(base) / .to_u64(base) (base is the radix, 2..36, default 10; supported by all integer conversion methods) / .to_float() / .to_string() / .to_string_base(base) / .abs() / .min(o) / .max(o) / .pow(e) / .mod(m) / .clamp(lo, hi).

    Conversion semantics (consistent with Rust as): narrowing truncates modulo 2ⁿ, u* is interpreted as unsigned, i* is sign-extended in two's complement; float → integer saturates to the target range.

    Two forms (consistent for all integer conversion methods):

    • The receiver must be a variable: conversion methods cannot be applied directly to literals; 11.to_i16() and "11".to_int(2) are both compile errors; bind with let first, then convert.
    • Without an argument: .to_i8() / .to_i16() / .to_u16()... only change the bit width, keeping the value (Rust as truncation / sign extension): let x: i8 = -5; x.to_i16() → -5, x.to_u8() → 251.
    • With an argument: .to_i8(16) / .to_i16(8)... first reinterpret the receiver's decimal representation in base (2..36), then change the bit width; the default 10 is equivalent to no argument: y.to_i16(8) → 45, y.to_i8(16) → 85, y.to_i16(10) → 55 (y = 55).
    • String receiver: let text: string = "ff"; text.to_u8(16) → ok(255), let text2: string = "755"; text2.to_u16(8) → ok(493), out of range returns err; a numeric receiver is reinterpreted and then truncated to the target width per Rust as; an illegal digit for that radix or a radix out of range (base must be 2..36) is a runtime error.

    3.4 Named Types

    type user = [name: string, age: int, tags: vec<string>];

    Rules:

    • Type declarations have exactly three spellings: type / struct / obj. All three are fully equivalent and interchangeable; a fourth keyword is not allowed.
    • The declaration form is fixed as keyword name = type; struct / obj are merely aliases with semantics identical to type.
    • Already-defined types may be referenced in nested form.
    • Type names are unique within a module (redefining the same type in one file is an immediate error).
    • Type definitions cannot be modified at runtime.

    Recursive types may reference themselves; in practice they must self-reference indirectly through a container such as vec / option / result / map to construct finite values:

    type node = [value: int, children: vec<node>];   // valid: indirectly via vec self-reference
type tree = [root: node];                        // valid: chained reference
type a = b;                                      // compile error: pure alias cycle, a concrete type can never be resolved
type b = a;

    Rules:

    • Alias expansion uses an "expansion stack": once an alias is already on the stack, expansion stops, so a recursive type is expanded only one level and neither grows exponentially nor overflows the stack.
    • A pure alias cycle (a cycle formed only by type x = y edges) has no container to break it and is reported statically as type 'x' is a recursive alias and never resolves.
    • A field type that is directly the type itself (type bad = [self_ref: bad]) passes the type check but cannot construct a finite value, being equivalent to always empty; whenever recursive data is needed, self-reference indirectly through vec / option / map.
    • Two recursive types may be assigned to each other as long as their structures are isomorphic: besides exact equality, same_type also performs a structural comparison with a depth limit of 32, so that "different expansion depths" are not mistaken for a type mismatch.

    3.4.1 Enumerations (ADT)

    type status = enum {
    active,
    pending,
    banned(reason: string),
}

type expr = enum {
    lit(value: int),
    neg(inner: expr),
    add(left: expr, right: expr),
}

    Rules:

    • Variants are separated by ,, and a trailing comma is allowed; a variant without fields is just its name.
    • Variant names are unique within an enum; the enum name shares a namespace with type / interface, and a name clash is an immediate error.
    • Construction: status.active (no fields), status.banned[reason = "spam"] (with fields; every field must be present and its type must match).
    • An enum is a Move type; use .clone() when two copies are needed.
    • Enums may define methods: func status.blocked(read s: status) -> bool { ... }, called as s.blocked().
    • An enum may reference itself or another enum recursively, and field types receive the same explicit type checking.
    • Enum values have no direct field access: reading a field requires match (see 9.3), which guarantees the field is taken according to the variant.
    • JSON serialization is {"variant": "banned", "reason": "spam"}; a fieldless variant has only variant.

    3.5 Inference Is Forbidden

    Every position must have an explicit type. The only exceptions are for item in xs and match arm bindings, whose types come from container/pattern destructuring and are not inference.

    // valid
let count: int = 0;
let name: string = "a";

// illegal (compile error)
count = 0;
count := 0;
tags = ["a"];
func f(x) -> int { return x; }
func f(x: int) { return; }

    4. Variable Definitions

    4.1 Four Kinds of Binding (the only spelling)

    let variable name: type = value;
let mut variable name: type = value;
const constant name: type = value;
static static variable name: type = value;

    Rules:

    • One of let / let mut / const / static must be written; no bare declaration.
    • The type must be written; no inference.
    • Statements end ; with a trailing semicolon.
    • const and static must be module-level and cannot be defined inside a function.
    • const is evaluated at compile time; static is initialized at runtime at a fixed address.
    • static mut requires an unsafe block and is forbidden at the user level.
    const MAX_SIZE: int = 1024;
static GLOBAL_COUNT: int = 0;

func main() -> void {
    let count: int = 0;
    let mut total: int = 0;
    total = total + 1;
    // count = 1;   // compile error: count immutable
}

    4.2 Read-only Variable Rules

    • let variables can only be read and cannot be assigned.
    • To "change a variable", create a new variable or use let mut.
    let x: int = 1;
let y: int = x + 1;     // carry the result in a new variable
// x = 2;               // compile error

let mut z: int = 1;
z = z + 1;              // valid

    4.3 Shadowing Is Forbidden

    Variable names are unique within a scope; a repeated declaration is a compile error.

    let x: int = 1;
let x: int = 2;         // compile error: x already defined

    5. The Three Data Structures

    5.1 ary (fixed-field named structure)

    Type definition (fields use :):

    type address = [city: string, zip: string];
type user = [id: int, name: string, address: address];

    Literal (fields use =, without repeating types):

    let mut u: user = [
    id = 1,
    name = "张三",
    address = [city = "北京", zip = "100000"]
];

    Access: dot notation only.

    u.name                  // read
u.address.city          // nested read
u.name = "李四";         // write, u must let mut

    Rules:

    • Field names are keys with dot access; u["name"] and u[0] are forbidden.
    • The field set is closed at compile time; at runtime only values can change, not fields.
    • To add a field: change the type definition and recompile, or define a new type + new variable (carrying values with .clone() from the old variable).
    • Dynamic growth: design the mutable part as a vec / map field and push / set into that field.

    5.2 vec (ordered sequence with implicit numeric keys)

    Types: vec<T> (homogeneous), vec<T1, T2> (heterogeneous, fixed length), vec (defined internally).

    Three legal forms:

    // pre-declared homogeneous + shorthand
let v1: vec<int> = [1, 2, 3];

// pre-declared homogeneous + explicit
let v2: vec<int> = [:int = 1, :int = 2];

// pre-declared heterogeneous + shorthand
let v3: vec<string, int> = ["a", 1];

// pre-declared heterogeneous + explicit
let v4: vec<string, int> = [:string = 'a', :int = 1];

// defined internally (elements carry their own types)
let v5: vec = [:int = 1, :string = "a", :bool = true];

// empty vec, type determined by the declaration
let v6: vec<int> = [];

    Illegal:

    let bad1: vec = [1, "a"];           // vec empty types cannot use the shorthand
let bad2: vec<int> = [1, "a"];      // homogeneous declaration; the second element type does not match
let bad3: vec<string, int> = [1, "a"];  // shorthand default type does not match the declaration

    Access:

    v.0                 // compile-time constant position
v.at(i)             // runtime position, returns result<T, string>

    Methods:

    v.len() / v.is_empty()
v.push(x) / v.pop() / v.insert(i, x) / v.remove(i) / v.clear()
v.reverse()                            // reversed, key reordering
v.sort(cmp: func(T, T) -> int)         // sorted, key reordering
v.map(f) / v.filter(f) / v.reduce(f, init) / v.find(f)
v.any(f) / v.all(f) / v.count(f)
v.slice(start, end) / v.concat(other) / v.unique() / v.flatten()
v.join(sep)                            // elements are string time
v.chunk(n) / v.zip(other)

    Rules:

    • Keys are always ordered 0,1,2... and are not exposed.
    • A homogeneous vec<T> supports push / pop / insert / remove / sort / reverse.
    • A heterogeneous vec<T1, T2> has fixed length; structural modification methods are compile errors and it is read-only.
    • The v[0] subscript is forbidden.
    • Default element types for literal shorthand [1, 2, 3]: 0 → int, "a" → string, 'a' → string, 1.5 → float, true → bool.

    5.3 map (dynamic key-value dictionary)

    let mut scores: map<string, int> = [];
scores.set("张三", 90);
scores.get("张三");          // option<int>
scores.has("张三");          // bool
scores.delete("张三");       // option<int>
scores.len();
scores.keys();               // vec<string>
scores.values();             // vec<int>
scores.items();              // vec<[key: string, value: int]>
scores.merge(other);
scores.filter(func(k: K, v: V) -> bool);

let config: map<string, string> = ["name" = "张三", "city" = "北京"];

    Rules:

    • K must be hashable (string / int* / bool).
    • Forbidden scores["张三"]; use only .get / .set / .has / .delete.
    • .get returns option<V>.
    • Backed by HashMap; unordered.

    6.2 Examples

    // Copy: assignment/passing as an argument keeps it usable

let b: int = a;
dev.log(a.to_string());    // a still usable

// Move: assignment transfers ownership
let s: string = "hello";
let t: string = s;
// dev.log(s);             // compile error: s invalidated

let u: user = [id = 1, name = "张三"];
let v: user = u;
// dev.log(u.name);        // compile error: u invalidated

    6.3 .clone()

    A Move type must provide .clone() methods that return a copy of the same type. This avoids a move in "define a new variable and carry the value over" scenarios.

    let u: user = [id = 1, name = "张三"];
let u2: user = u.clone();     // u still usable

    7. Functions and Ownership

    7.1 Function Definitions (the only spelling)

    func name(parameter, ...) -> return type {
    statement;
    return value;
}
    func add(a: int, b: int) -> int {
    return a + b;
}

func log(msg: string) -> void {
    // write when nothing is returned -> void
}

    Rules: parameter types must be written; the return type must be written, using -> void when nothing is returned; fn / def / function and arrow functions are not introduced.

    7.1.1 Package-internal Visibility self

    Functions are publicly visible by default. With the self modifier they can be called only inside the package that declares them:

    self func hash_password(raw: string) -> string {
    return raw;   // for use only inside this package
}

    Rules:

    • The spelling is unique: self func name(...); self occupies the position before pub and cannot appear together with pub.
    • self func can be called only by functions in the same package (same directory); cross-package calls, passing the function as a value, or passing it as a callback are all compile errors.
    • The check happens at compile time and applies equally to rip check / rip run / rip build.
    • Package boundaries follow the mod declaration of the file containing the function; in project mode each directory is a package.
    • Functions without self keep the current global visibility, and pub may be written or omitted.

    7.2 Parameter Modifiers (read / write, may be written as &T / &mut T)

    SpellingUnderlying RustSemantics
    OmittedTCopy duplicate / Move transfer
    read name: T / name: &T&TRead-only access; the original variable is retained
    write name: T / name: &mut T&mut TWritable access; the original variable is retained, and the argument must be let mut

    Rules:

    • mut is used only in let mut and is not a parameter modifier.
    • Writing read / write on a Copy type parameter emits a warning (it has no real meaning).
    • Only read / write remain as parameter modifiers; &T / &mut T are equivalent spellings with identical compilation results.
    • A parameter may use only one spelling; mixing, as in read u: &user, is an immediate error.
    • & / &mut appear only in parameter type positions; let x: &T is not a legal type.
    • Lifetimes are still inferred by the compiler; users never write 'a.
    func greet(read u: user) -> string {
    return "Hi " + u.name;
}

func rename(write u: user, n: string) -> void {
    u.name = n;
}

func consume(u: user) -> int {       // default, u move in
    return u.id;
}

    7.3 Calling

    let mut u: user = [id = 1, name = "张三", address = [city = "北京", zip = "1"]];

let msg: string = greet(u);          // read, u retained
rename(u, "李四");                    // write; u retained and modified
let id: int = consume(u);             // default, u move, invalidated afterwards

    7.4 Lifetimes

    • Users never write 'a.
    • A returned reference can only come from the sole input reference:
    func get_name(read u: user) -> read string {
    return u.name;
}
    • Returning a reference from multiple input references → compile error; the signature must be changed.
    • The compiler infers with NLL plus tightened rules; when it cannot infer, it reports an error directly.

    7.6 Closures

    let double: func(int) -> int = func(x: int) -> int {

    7.7 Generic Functions

    Type parameters are written in <...> after the function name and may be referenced by parameter types, return types, and container types:

    func identity<T>(x: T) -> T {
    return x;
}

func size<T>(read items: vec<T>) -> int {
    return items.len();
}

let n: int = identity(1);              // T inferred as int
let s: string = identity<string>("a"); // explicit type argument

    Rules:

    • Inferred or explicit: identity(1) infers from the arguments; identity<string>("a") specifies explicitly, and the count must match the declared type parameters.
    • Constraints: func total<S: shape>(read items: vec<S>) -> float; the constraint name must be an interface. Inside the function body, methods on S resolve through that interface (item.area()), and call sites check whether the argument type implements the interface.
    • A type parameter that is declared but cannot be inferred (it appears only in return position) is treated as any, with no implicit assignment from any to a concrete type.
    • Runtime type erasure: no monomorphization; a generic function has a single implementation in the interpreter / bytecode / AOT, with no extra runtime overhead.
    • Inside a function body, a type parameter is opaque when unconstrained: it can only be passed around as a whole (as an ordinary parameter, container element, return value, or payload of some / ok) and cannot have methods called on it or be used with literals; when such operations are needed, add an interface constraint or rewrite with a concrete type.
    • Generic functions are not overloaded: a function with the same name counts as a redefinition regardless of differing type parameters; use a different name when needed.
    • rip build AOT artifacts also support generic functions: type parameters participate only in compile-time checking and do not exist at runtime.

    7.8 Methods and Interfaces

    Methods: func type.method(...); the first parameter is the receiver, which may be only read or write.

    type user = [id: int, name: string];

pub func user.display(read u: user) -> string {
    return u.name;
}

func user.rename(write u: user, name: string) -> void {
    u.name = name;
}

let mut u: user = [id = 1, name = "张三"];
u.display();          // statically dispatched to user.display(u)
u.rename("李四");     // write: the receiver requires u to be let mut

    Rules:

    • The full name is type.method (e.g. user.display) and is globally unique in the function table; a method name is unique within its type.
    • The receiver must be written explicitly (read u: user / write u: user); self / this are not introduced.
    • write receivers require the receiver to be a mutable variable or a field chain; a temporary value (make().rename(...)) is an immediate error.
    • Methods cannot carry annotations, cannot be generic, and cannot be modified with self.
    • Methods may be pub; type visibility is still determined by pub type.
    • Enums can carry methods too: func status.blocked(read s: status) -> bool, called as s.blocked().

    Interfaces: type name = interface { ... }, listing method signatures only, with the receiver fixed to the interface itself.

    pub type shape = interface {
    func area() -> float
    func name() -> string
    write func scale(factor: float) -> void
}

type circle = [radius: float];
type square = [side: float];

func circle.area(read c: circle) -> float { return 3.0 * c.radius * c.radius; }
func circle.name(read c: circle) -> string { return "circle"; }
func circle.scale(write c: circle, factor: float) -> void { c.radius = c.radius * factor; }

func describe(read s: shape) -> string {
    return s.name() + " area=" + s.area().to_string();
}

let shapes: vec<shape> = [circle[radius = 1.0], square[side = 3.0]];
for s in shapes {
    dev.log(describe(s));      // dispatched by class name at runtime to circle / square method of
}

    Rules:

    • Implicit implementation: a concrete type that has methods with the same names and signatures required by the interface is considered an implementation; no impl declaration is needed.
    • Signatures must match exactly: parameter types, return types, and receiver mode (write corresponds to write).
    • Interface values can be placed in vec, used as parameters/return values, or used as ary fields; calls dispatch by runtime class name.
    • Construct interface values with named constructors (circle[radius = 1.0]) or variables already declared with a concrete type; the runtime records the class name accordingly.
    • Only user-named types (type x = [...]) can implement interfaces; built-in types (string / int etc.) do not participate.
    • Interfaces share a namespace with type; a name clash is an immediate error; method implementations cannot be written for an interface (func shape.x is an error).

    7.9 defer / Resource Release

    defer call; executes this call when the current function exits, and is used to close connections, unlock, and clean up temporary resources.

    func read_file(path: string) -> result<string, string> {
    let conn: conn = open(path);
    defer conn.close();          // arguments are evaluated in place at defer the defer statement
    let content: string = conn.read()?;
    return ok(content);
}

    Rules:

    • Only call expressions are accepted: defer f(...) / defer x.m(...) / defer module.f(...); defer 1 + 2; is a syntax error.
    • Arguments are evaluated immediately at the defer statement, and on function exit only the call itself runs (Go semantics). Hence defer f(x) captures the value at that time, and changing x later has no effect.
    • Last in, first out: multiple defer statements in the same function run in reverse order of registration.
    • Executed on every exit path: normal return, return value, ? propagation, return err(...), and runtime errors all trigger the current frame's defer.
    • Isolated per function frame: defer belongs to the frame that registered it; when an inner function returns, only items registered in that inner frame run.
    • Return values are discarded: the call's return value in defer does not participate in any expression.
    • defer can be used only inside a function body: writing parallel at the top level or in a defer branch is a compile error.
    • defer itself failing overrides the function's original exit result.
    func demo() -> void {
    defer print("first");        // executed last
    defer print("second");       // executed first
    print("body");
}
// output: body / second / first

    +  -  *  /  %

    Rules: operands must be of the same type and the result has the same type; direct operations between different integer types are forbidden and require explicit conversions such as .to_i8() / .to_u8(); division by zero panics.

    8.2 Comparison (same type, returns bool)

    ==  !=  <  >  <=  >=

    8.3 Logic (bool)

    &&  ||  !

    8.4 String Concatenation

    "a" + "b"       // "ab"

    Only string + string, with no implicit conversion.

    8.5 Type Conversion

    The only spelling: a method on the target type:

    let a: u8 = 0b1010;
let b: int = a.to_int();

let s: string = "42";

    9. Control Flow

    9.1 Conditionals

    if condition { ... } else if condition { ... } else { ... }
if condition { ... } elif condition { ... } else { ... }

    The condition must be bool; there is no truthy/falsy; parentheses may be omitted.

    if score >= 90 {
    dev.log("A");
} elif score >= 80 {
    dev.log("B");
} else {
    dev.log("C");
}

    9.2 Loops (four forms, same rules as Rust)

    Form 1: loop — an unconditional loop that can be exited only with break.

    let mut count: int = 0;
loop {
    if count >= 10 { break; }
    count = count + 1;
}

    Form 2: while — the condition is bool; check first, then execute on each iteration.

    let mut count: int = 0;
while count < 10 {
    count = count + 1;
}

    Form 3: while let — evaluate the expression and match the pattern on each iteration; the body runs only when the match succeeds, otherwise the loop ends. = binds the pattern and => introduces the body.

    while let some(value) = cache.get("key") => {
    dev.log(value);
    cache.delete("key");
}

    Form 4: for ... in — iterates over vec (elements) or map (keys).

    for item in tags {
    // item type from tags element type destructuring
}

for key in scores.keys() {
    // key: string
}

    Rules:

    • break / continue affect only the innermost loop; continue returns to the condition check (for-in goes to the next iteration).
    • A loop condition must be bool; no truthy / falsy.
    • There is no do-while and no C-style three-part for.
    • Loop bodies must use braces.

    9.3 Pattern Matching

    match expression {
    pattern1 => { statement }
    pattern2 => { statement }
}

    match arms use =>; = is used only for binding and assignment. This is one of the only two uses of => (the other is while let).

    match result {
    ok(v) => { print(v); }
    err(e) => { print("error: " + e); }
}

match opt {
    some(x) => { print(x); }
    none => { print("empty"); }
}

match user {
    [id: int, name: string, address: _] => { print(name); }
}

match state {
    status.active => { print("ok"); }
    status.pending => { print("wait"); }
    status.banned[reason: string] => { print(reason); }
}

    Rules: match must be exhaustive and is checked by the compiler; it is used for option / result / ary destructuring and enum variants; while let need not be exhaustive, and the loop simply ends when the match fails.

    • An enum pattern is written enum name.variant; a variant with fields binds them with [field: type, ...] (_ means no binding).
    • Exhaustiveness is checked by variant name: a missing variant reports match on enum 'x' must cover variant 'y'.
    • The enum name in a pattern must match the subject type, field names must belong to that variant, and field type annotations must match the declaration.
    • Enum values do not support direct field access (s.reason is an error); fields must be extracted through match.
    • Enum patterns can also be used with while let: the loop ends when the variant does not match, and exhaustiveness is not required.

    9.4 Error Propagation

    func read_config(path: string) -> result<string, string> {
    let content: string = read_file(path)?;
    return ok(content);
}

    ? may be used only inside a function returning result; for err(e) it immediately returns err(e).

    10. Modules and Imports

    10.1 Module Declaration (mod)

    The first line of every .rp file:

    mod user_api;

    Rules:

    • The module name must equal the directory name containing the file, exactly, using a single snake_case segment and no dotted name.
    • All .rp files in the same directory must declare the same module name.
    • Subdirectories are independent modules, and their module names likewise equal the subdirectory name.
    • A missing mod declaration, a module name that differs from the directory name, or inconsistent module names in the same directory all fail compilation immediately.
    • mod foo; does not pull in submodule files: within a project, .rp files are collected recursively by the project loader and merged; mod only declares the current file's module identity.

    10.2 Module Imports (use)

    Rust-style path segments are used, but calls still keep Rip's dot form:

    use std::http;
use std::json;
use std::sys as sys;
use github::com::user::pkg as pkg;
use rust::serde_json as json;

    Rules:

    • Paths are segmented with :: and are not quoted; a path has at least one segment.
    • as is followed by an alias, which must be a legal identifier; as is the only renaming mechanism.
    • Without an alias, the last path segment is used as the alias by default (std::http → http).
    • Only modules are imported; item-by-item imports are not supported (use std::http::serve; is an error), consistent with "exactly one way".
    • The std prefix is the standard library, rust is a Rust crate, and everything else is a third-party Rip package.
    • After an import, calls are written alias.function(...); the :: call form is not introduced; method calls on values remain value.method().
    • Third-party packages live under the project root packages/ (package/ is also accepted; when both exist, packages/ takes precedence); the use path is the path relative to the package directory with / replaced by ::: packages/utils/http.rp → use utils::http;; package names may have multiple segments, and precompiled .rpa packages are equivalent to .rp source packages.
    • Third-party packages are merged with the project source into the same compilation unit at compile time; pub functions inside a package are called by their ordinary function names (http.client(...) is resolved by the alias to the global function of the same name); after merging, function, type, and global variable names must be globally unique, and a conflict is reported before type checking together with both declaration locations.
    • Source files inside a package are not subject to the "module name must equal directory name" check; package identity is determined by its path under packages/.
    • import is not a keyword: writing import "std/http"; only produces a syntax error.

    10.3 Visibility

    Private to the module by default; pub makes it public:

    pub func serve(port: int, handler: func(http.request) -> http.response) -> void { ... }
pub type user = [id: int, name: string];

    Rules: there are only two levels, "private by default / public with pub "; private / protected are not introduced.

    10.5 Third-party Packages and Precompiled Packages .rpa

    Project root conventions:

    myapp/
├── main.rp
├── rip.toml
└── packages/
    ├── utils/http.rp          # source package: path utils/http
    ├── utils/strings.rp
    └── vendor/logger.rpa      # precompiled package: path vendor/logger
    • Imported in exactly the same way as source packages: use utils::http;, use vendor::logger as logger;.
    • Source and precompiled packages may be mixed; what actually takes part in compilation is everything under packages/: all .rp and .rpa.
      • Directory input: recursively merges the .rp files inside the directory and produces <dir name>.rpa in the same directory;
      • File input: produces an .rpa with the same name;
      • The artifact header records rip-package 1, rip-version, and the package name; rip build reports an error and refuses to load when the versions do not match.
    • packages/, like tests/ and dist/, is not collected as project source; it is handled only by package-loading logic.
    • Packaged delivery: packages are embedded into the executable by default (both flat and typed); the typed layout additionally copies them to lib/packages/. To distribute source packages separately, simply copy the packages/ directory at the project root.

    Project mode (multi-file compilation unit):

    • A directory that contains rip.toml is treated as a project, and rip run / rip dev / rip build / rip check all operate on projects.
    • Compilation unit = the entry + all .rp files collected recursively within the project; tests/, build/, dist/, target/, node_modules/, and directories beginning with a dot do not take part in compilation; data directories etc. are declared by [compile] exclude (directory names or paths relative to the project root, such as storage, data/db), and the toolchain does not build in special cases such as storage/, uploads/.
    • The names of runtime data directories (databases, user uploads) are decided entirely by code: the first argument of http.save_file and the connection path of std/db are ordinary strings, and whatever directory is written is the directory used; to skip such a directory at compile time, just add it to [compile] exclude.
    • [compile] exclude and [build] copy are independent: the former affects only source collection, the latter only packaging copies.
    • rip test <project dir> merges packages/ in project mode and then runs all #[test] functions uniformly; #[test] is not executed when there is no main (main may be a long-running service). When a directory is not a project, each .rp file is compiled and tested individually.
    • The entry is taken from [module] entry; when unset, <dir name>.rp, main.rp, src/main.rp are tried in order. The entry must contain func main() -> void.
    • Each file still declares its own mod directory name;, with the same directory and module; cross-file calls use the function name directly, without use for local files (use is only for std::*, rust::*, and external Rip packages).
    • Function, type, and constant names are unique within a compilation unit; a duplicate name fails compilation immediately.
    • Diagnostics must map back to the original file and line number: relative path:line: error: ....
    • Without rip.toml, files are handled individually, with behavior exactly the same as single-file mode.
    • [runtime] log controls the language of the runtime's own messages: "english" (default) or "chinese"; any other value is treated as the default. This affects only runtime errors, HTTP and WebSocket startup messages, background task and scheduled task logs, and std/log level labels; it does not affect the print output of Rip programs themselves, nor does it change the result error values returned to programs. Compile-time diagnostics (lexing, syntax, types, ownership checks) always use English. rip build writes this configuration into the artifact, so rip.toml is no longer needed after delivery.

    10.6 Rust Package Interop (the only way)

    Goal: a Rust package is just an ordinary package in Rip, called entirely with Rip syntax, exposing no Rust-specific syntax (no &, no 'a, no unsafe, no Box, no impl).

    Importing and calling:

    use rust::serde_json as json;

let s: result<string, string> = json.to_string(user);
let v: result<any, string> = json.from_str(s);

    Type mapping (fixed, not extensible):

    RustRip
    i64int
    i8 / i16 / i32 / i64i8 / i16 / i32 / i64
    u8 / u16 / u32 / u64u8 / u16 / u32 / u64
    f64 / f32float
    String / &strstring
    boolbool
    Vec<T>vec<T>
    HashMap<K, V>map<K, V>
    Option<T>option<T>
    Result<T, E>result<T, E>
    ()void

    In the table, ary is Rip's structural type; the declaration keyword may be written type / struct / obj, and the three are strictly aliases (see 3.4). The mapping table is fixed; package authors cannot extend it or add aliases.

    Rip declaration files: a Rust package author must provide .rp.decl interface declarations describing the Rip signatures of the exported functions:

    // serde_json.rp.decl
pub func to_string(v: any) -> result<string, string>

    Safety boundary:

    • unsafe is confined to the Rust package and does not leak into the user level.
    • References &T / &mut T are not exposed to the user level; values are returned or own semantics apply.
    • A panic must be caught by the package and converted to result; it must never propagate into the Rip runtime.
    • Rust packages are compiled at toolchain release time and statically linked into rip; the user's machine does not run cargo and needs no Rust environment.
    • rip add rust:xxx records intent only; whether a Rust package can be used depends on whether the current rip already bundles it. The current version bundles rust/serde_json; new crates must be included when releasing rip (see 10.11).

    Constraints:

    • use rust::xxx; is the only import mechanism.
    • Second mechanisms such as extern / ffi / cgo are not introduced.
    • The type mapping is fixed; package authors cannot extend it.
    • A Rust package can cover any domain (including GUI, audio/video, database drivers, etc.); Rip does not restrict package types, only the calling convention. This version's standard library provides no GUI wrapper; GUI needs are integrated through use rust::xxx;.
    • To add Rust capabilities without republishing rip, use the native packages of 10.12 (dynamic library + .rp.decl); the trade-off between bundling and new crates is discussed in that section.

    Common options:

    OptionEffect
    --offlineUse only packages already available locally; requires rip.lock to exist and pass verification
    --deny-warningsTreat warnings as errors (for CI)

    rip test rules:

    • Test functions are written #[test] func test_xxx() -> void { dev.assert(...); } and take no parameters.
    • Project mode merges the project source with packages/ and then runs everything uniformly; non-project directories are collected file by file, and directory scanning does not execute main (main may be a long-running service) — only compile checks and #[test] tests run; #[test] is executed without main only when a single file is passed explicitly.
    • Outputs test <file>.<function> ... ok / FAIL, and finally N passed, M failed.
    • --filter <name> runs only tests whose function name contains the substring.
    • Isolation: each #[test] uses a fresh runtime, and module-level const / static and runtime resources (database connections, network handles, timers) are not shared; --no-isolate switches to one runtime per file (faster, but state leaks across tests).
    • Concurrency: tests run in parallel by default using the number of CPU cores (each thread creates its own runtime); --jobs N sets the thread count and --jobs 1 forces serial execution. Results are printed by file and declaration order, independent of execution order. --no-isolate permits serial execution only.
    • Timeouts: 30 seconds per case by default; --timeout <ms> adjusts it and 0 disables it. A timeout is interrupted at checkpoints in statements / loop iterations / built-in calls; a single blocking system call cannot be interrupted midway. When tests use shared external resources (a fixed port, the same database file), use --jobs 1 to avoid interference.

    10.8 Dependency Locking and Static Checks

    rip.lock (dependency locking):

    • rip lock scans all packages/ / package/ files under the project's .rp / .rpa), records each package's name, version, source path, SHA-256, and direct dependencies, and writes them to rip.lock at the project root.
    • rip run / rip dev / rip build / rip check / rip test automatically verify when rip.lock exists: changed package contents, a missing package, or a newly added unrecorded package are all errors that prompt re-running rip lock.
    • Without rip.lock, behavior is as before (no verification); in --offline mode it is mandatory to have rip.lock, ensuring offline environments never pick up unlocked dependencies.
    • [registry] source records the private package source URL (written into the rip.lock field of registry); [registry] offline = true is equivalent to always passing --offline.
    [registry]
source = "https://rip.example.com"
offline = false

    Static checks (rip check / compile-time warnings):

    • Unused variable: a local variable declared with let is never read; names starting with _ are not checked.
    • Unused import: the alias from use is used neither for calls nor for pkg.type types; warning only. Third-party packages (under packages/) are merged with source at compile time and calls do not go through the alias, so they are not subject to this check.
    • Unused private function: self func is never called (functions with route/task/test annotations do not count).
    • Package cycles: when two or more packages under packages/ reference use each other, warning: package cycle: a -> b -> a is printed.
    • All of the above are warnings, which --deny-warnings can escalate into failures.

    Formatting (rip fmt):

    • Unified 4-space indentation: realigned by {} / [] / () nesting level, with leading closing symbols returning to their matching level.
    • Trailing whitespace on each line is removed, consecutive blank lines are collapsed into one, and the file ends with a single newline.
    • Adjacent use ...; blocks are sorted by path.
    • Triple-quoted template strings and the inside of /* */ comments are kept as is and not reflowed.
    • Supports files or directories (recursively); --check only checks and exits with code 1 to mean "needs formatting", while --stdout prints the result without writing it back.

    • Package sources support local directories, file://, and https://. Online sources must use https: only localhost / 127.0.0.1 / ::1 may use http:// (for local development); any other http:// source is rejected outright, preventing man-in-the-middle replacement of package contents. When an online package source is configured, rip lock / rip vendor / rip run resolve constraints per [dependencies], solve versions, download and verify sha256, and unpack into packages/; downloads from remote sources must carry the index sha256, and a missing digest refuses the download (local directory sources are exempt from this). Offline (--offline or [registry] offline = true) uses only existing local packages and requires rip.lock verification to pass.
    • Version solving: bounded depth-first search with backtracking. Only one version is selected per package; candidates are tried in descending version order, falling back to earlier candidates on dependency conflicts. When there is no solution, the origin of each constraint is reported (rip.toml or a specific version of some upstream package).
    • Package source index: v1/index/<name> holds all versions of a single package; v1/index.json is the index for online sources, organized by directory; archives live in v1/packages/<name>/<version>.zip and sha256 is recorded in the index. rip pub rebuilds v1/index.json automatically when writing a local package source.
    • [dependencies] versions are semver constraints (^0.1.0, ~1.2, 1.2.*, *, etc.); rip add <package>[@constraint] writes the manifest and fetches immediately (equivalent to subsequently running rip lock).
    • [registry] source writes the rip.lock field of registry, making the source auditable.
    • rip search <keyword> and rip info <package name> let you inspect package source contents (--registry overrides the source temporarily, --json outputs structured results).

    10.12 Native Packages (Rust plugins)

    Native packages let Rip call capabilities implemented in Rust, while the user side still needs only rip. Signatures come from .rp.decl and the implementation comes from a platform dynamic library (under AOT it can be linked statically).

    1) Directory conventions

    <root>/acme/tools/
├── package.decl      # interface declarations (the only source of signatures)
├── tools.dll         # Windows; Linux is libtools.so, macOS is libtools.dylib
└── libtools.a        # optional: static library (Rust staticlib), for --aot static linking

    The package path is the relative path; in code you write use acme::tools;. The search roots, in order, are:

    1. RIP_NATIVE_PATH (several entries separated by the path separator; for troubleshooting/custom installation)
    2. <rip>/lib/rip/plugins: native packages distributed with the toolchain
    3. <executable>/lib/native: native packages distributed with the delivered artifact
    4. the current working directory's lib/rip/plugins and lib/native

    2) Declaration file

    abi = 1
platform = "windows-x86_64"
sha256 = "..."                 // optional: dynamic library digest; when set it is enforced
prefix = "acme"              // optional: symbol prefix, used when several native packages coexist

pub func shout(text: string) -> string
pub func fail(msg: string) -> result<string, string>
    • abi must match the current rip (version 1 in this release).
    • platform is <os>-<arch>; x64/amd64 are equivalent to x86_64.
    • prefix allows only ASCII letters, digits, and _.
    • Types support int/float/string/bool/any/void, vec<T>, map<K,V>, option<T>, result<T,E>, share<T>.

    3) Plugin ABI

    The dynamic library exports four C symbols:

    uint32_t rp_native_abi(void);
const uint8_t *rp_native_decl(size_t *out_len);      // returns the same content as package.decl same content
uint8_t *rp_native_call(const uint8_t *name, size_t name_len,
                        const uint8_t *args, size_t args_len,
                        size_t *out_len);
void rp_native_free(uint8_t *ptr, size_t len);
    • Arguments are a JSON array; the return value is {"ok": …} or {"err": "…"}.
    • When prefix = "acme" is written in the declaration, the four symbol names all become rp_native_acme_abi / rp_native_acme_decl / rp_native_acme_call / rp_native_acme_free.
    • For a function declared to return result<T,E>: err becomes an err(...) value; for a function returning other types, err is thrown as a runtime error.
    • Panics must be caught inside the plugin with catch_unwind; they must never cross the ABI.
    • Checked on load: the ABI version, platform, sha256, and whether the plugin's embedded declaration matches package.decl.

    4) The two execution modes

    ModeLoad timingDelivery requirement
    rip runLoaded from the search roots on the first callThe native package directory is in place (working directory or RIP_NATIVE_PATH)
    rip buildLinked at compile time when a static library exists; otherwise loaded at runtimeStatically linked packages need no delivery; the rest are copied to <artifact>/lib/native/<package path>
    • Static link fast path: when lib<name>.a (Linux/macOS/Windows-GNU) or <name>.lib (Windows-MSVC) exists in the package directory,

    rip build links it directly into the executable via #[link(name = "…", kind = "static")], so the artifact is still a single file and no lib/native/ is produced; the ABI version is verified at startup, and signatures still come from package.decl. A plugin can provide both forms at once with crate-type = ["cdylib", "staticlib"].

    • .dll.a / .dll.lib are dynamic library import libraries and are not treated as static libraries.
    • Multiple native packages coexisting: when package.decl is written in prefix = "acme", the four ABI symbols carry the prefix, so any number of prefixed packages can be statically linked into one artifact at the same time.

    Packages without a prefix share fixed symbol names, so only one can be statically linked into an artifact; the rest fall back to dynamic loading in package-path order, with a notice at build time.

    • rip build copies only the native packages the program actually uses; README.md lists them one by one (statically linked ones are marked "statically linked").
    • Native packages are binary files, so they are unaffected by "deliverables contain no source"; when no native packages are used (or all are statically linked), the artifact is still a single file.

    5) Minimal plugin implementation

    const DECL: &str = "abi = 1\nplatform = \"windows-x86_64\"\n\npub func shout(text: string) -> string\n";

#[no_mangle]
pub extern "C" fn rp_native_abi() -> u32 { 1 }

#[no_mangle]
pub extern "C" fn rp_native_decl(out_len: *mut usize) -> *const u8 {
    unsafe { *out_len = DECL.len() };
    DECL.as_ptr()
}

#[no_mangle]
pub extern "C" fn rp_native_call(_: *const u8, _: usize, args: *const u8, args_len: usize, out_len: *mut usize) -> *mut u8 {
    let args: serde_json::Value = serde_json::from_slice(unsafe { std::slice::from_raw_parts(args, args_len) }).unwrap();
    let text = args.get(0).and_then(|v| v.as_str()).unwrap_or("");
    let body = serde_json::to_vec(&serde_json::json!({ "ok": text.to_uppercase() })).unwrap();
    let mut boxed = body.into_boxed_slice();
    unsafe { *out_len = boxed.len() };
    let pointer = boxed.as_mut_ptr();
    std::mem::forget(boxed);
    pointer
}

#[no_mangle]
pub extern "C" fn rp_native_free(pointer: *mut u8, len: usize) {
    unsafe { drop(Box::from_raw(std::ptr::slice_from_raw_parts_mut(pointer, len))) };
}

    Build: cargo build --release ([lib] crate-type = ["cdylib"]; write ["cdylib", "staticlib"] if AOT static linking is desired), then place the dynamic library (and optionally the static library) plus package.decl into the directories described above. To coexist with multiple packages, rename the four #[no_mangle] functions to prefixed names per the table above and write the same package.decl in prefix.

    Core rules:

    • http.response is just an ordinary ary; whatever the user return is what gets sent, and the framework enforces no format.
    • body field: returns a raw string; the framework sets no Content-Type; the user writes headers themselves.
    • json field: an optional convenience sugar. When the user assigns ary / vec / map to the json field, the framework serializes it and sets Content-Type: application/json.
    • sse field: used when the user explicitly chooses SSE. Response headers are sent first, events are flushed frame by frame, and the stream ends when the client disconnects; one connection occupies one interpreter thread, so raise [server] workers when there are many long-lived connections.
    • body / json / sse : choose exactly one, checked for mutual exclusion at compile time.
    • Middleware: http.chain([mw...], handler) wraps in order, composed and cached on the first request; mw is func(next handler) -> new handler. http.cors("*") handles OPTIONS preflight automatically, http.security_headers() adds security headers, http.with_headers(map) appends fixed headers, and http.rate_limit(rate, burst) applies route-level rate limiting per client IP. http.group(prefix, [mw...], [routes...]) lets routes in a group use relative paths, registering the whole group as one prefixed route.
    • OpenAPI: http.openapi(router, title, version) generates OpenAPI 3.0 JSON from the route table (paths, methods, operationId, path parameters); call it once after the route table is built.
    • Request context: req.ctx is a map<string, any>; middleware write to it (e.g. the current user) and handlers read from it, sharing the same map within a request.
    • Response compression: text responses of 1 KiB or more are gzip-compressed per Accept-Encoding, with Vary: Accept-Encoding added; static files and SSE are not compressed. No handling is needed in business code.
    • Static assets: http.static responses carry ETag / Last-Modified / Cache-Control and support If-None-Match (304) and single-range Range (206 / 416); files are streamed from disk without occupying interpreter memory; HTML uses no-cache, and everything else is cached long.
    • Sessions and validation: std/session provides stateless cookies signed with HMAC-SHA256 (save / cookie / load / clear / csrf_token / csrf_check), and multiple instances need no shared storage; std/validate expresses field validation in one line and returns readable errors. std/jwt provides HS256 sign / verify (verification forces the HS256 algorithm and rejects none). Keys must come from environment variables or configuration. When the server enables HTTPS (--cert / --key), the save / cookie / Set-Cookie automatically gets the Secure attribute.
    • Templates: std/template.render(source, data) escapes HTML by default and supports if / unless / each / comments; compiled results are cached per source in thread-local storage, suitable for server-side rendering.
    • Returning HTML: body + headers = ["Content-Type" = "text/html; charset=utf-8"].
    • Returning JSON: use the json field (sugar), or call json.encode yourself and put the result in body plus handwritten headers (manual). Both are allowed; their semantics differ, and this is not a second spelling.
    • multipart/form-data requests are parsed automatically: ordinary fields are merged into form and files go into files; http.save_file(dir, file) decodes data_base64, sanitizes the file name, and writes it to a directory (created automatically when missing), returning the written path or err(...). The directory argument is an ordinary string decided by code; there is no built-in upload directory at runtime.
    • http.fetch performs outbound requests: supports http / https (validated against system root certificates), any method and headers, and a string body, returning status / headers / body. Used for calling third-party APIs, webhooks, etc.; the target address and credentials are entirely given by code, and the runtime applies no allowlist or directory restrictions. http.fetch_file behaves the same, except the request body is read directly from the file's raw bytes, suitable for uploading images, videos, and other binary content. http.download(url, headers, path) writes the response body's raw bytes to a file and returns the byte count, suitable for downloading binary objects. Connection timeout is 30 seconds; read/write timeout is 60 seconds; HEAD reads only the response headers, not the body.
    • Object storage belongs to the Rip layer and is not built into the runtime: S3 / OSS / COS are all public HTTP protocols plus signature specifications, and can be implemented in Rip code or third-party packages with http.fetch / http.fetch_file / http.download plus std/crypto (sha256, hmac_sha256_hex, sha256_file) and std/encode (url_encode); the repository ships examples/s3_demo/packages/s3 as a reference implementation (AWS SigV4, compatible with S3-compatible services such as MinIO / R2 / B2). The runtime provides only generic HTTP and cryptographic primitives, introducing no vendor SDKs or protocol branches.
    • http.fetch_retry(..., attempts) retries with 100ms × attempt backoff on connection failure or a 5xx response, where attempts is 1..5; if it still fails, it returns the last response (5xx) or err(...). Suitable for transient failures when calling cross-machine services, object storage, etc.; business errors (4xx) are not retried.

    Server runtime semantics (mandatory):

    • Concurrency: plaintext HTTP connections are managed by tokio (keep-alive does not occupy a thread; the number of I/O threads scales with CPU cores, bounded to 4–16), and handlers run on a fixed number of interpreter threads (CPU cores by default, overridable with [server] workers); requests are dispatched to the least busy interpreter thread by "remaining queue capacity", avoiding head-of-line blocking caused by a single slow route; response headers and body are combined into one write; TLS still uses one worker thread per connection. Each thread owns an independent interpreter, and static / global variables are isolated per thread and not shared across requests; use Redis, a database, or files when shared state is needed.
    • Connection reuse: HTTP/1.1 keep-alive is supported; connections are closed after being idle longer than [server] keep_alive_ms or reaching max_requests.
    • Timeouts: read and write timeouts are controlled by [server] read_timeout_ms / write_timeout_ms, preventing slow connections from occupying threads for long.
    • Rate limiting and backpressure: the connection queue limit is max_connections; beyond it, 503 is returned immediately and the connection is closed; a request body larger than max_body_bytes returns 413; an over-limit request line or headers return 413. Content-Length and Transfer-Encoding: chunked are supported.
    • In-process rate limiting: [server] rate_limit enables a token bucket (refilled per second); exceeding it returns 429 + Retry-After: 1 without entering the handler; with rate_limit_per_ip = true buckets are per client IP, and rip_http_rate_limited_total counts the events. When multiple instances need a global quota, switch to std/redis of rate_limit.
    • Reverse proxy: set [server] trust_proxy = true when deployed behind a trusted proxy; the client IP is the leftmost valid address in X-Forwarded-For (falling back to X-Real-IP), and access logs, rate limiting, and req.client_ip all apply; in direct-connection scenarios keep false, otherwise clients can forge IPs. The safer approach is trusted_proxies = "10.0.0.0/8,...": forwarded headers are trusted only for requests from those network ranges, restoring the real client hop by hop. When trust_proxy = true is enabled but trusted_proxies is not configured, startup prints a warning that any client can forge X-Forwarded-For.
    • Fault isolation: a runtime error in one request affects only that request (returning 500); a panic in a worker thread is caught and subsequent connections continue to be served.
    • Graceful shutdown: upon SIGINT / SIGTERM (Ctrl+C on Windows), accepting stops, already-queued connections are finished, and then the process exits; during shutdown /readyz returns 503.
    • Built-in endpoints: GET /healthz always returns 200 ok (liveness probe); GET /readyz returns 200 ready when not shutting down and 503 while shutting down; when [server] metrics_path is non-empty, that path returns metrics in Prometheus text format. All three paths are handled before user routes, and they can be changed or disabled by setting them empty in [server].
    • Request ID: when X-Request-Id is missing, req-<time>-<sequence number> is generated, written to http.request.request_id, and echoed in the response header; the JSON format of std/log automatically includes this field.
    • Metrics: http.metrics() returns the same Prometheus text as the built-in endpoint, for custom exposure paths.

    11.2.1 Route Annotations (the default registration method)

    Functions with route annotations are registered when the http.router is built automatically; there is no need to write them again in an explicit route table:

    #[get("/api/users")]
func users_index(read req: http.request) -> http.response {
    return http.response[status = 200, json = [items = []]];
}

#[post("/api/users")]
func users_create(read req: http.request) -> http.response {
    return http.response[status = 201, json = [id = 1]];
}

func main() -> void {
    let extra: vec<http.route> = [http.static("/", "public")];
    http.serve(8080, http.router(extra));
}

    Rules:

    • A function with a route annotation has the fixed signature func(read req: http.request) -> http.response: exactly one http.request parameter, returning http.response. The parameter may omit read but cannot be write.
    • Annotations provide only the method and path; request parsing and response assembly are done by the function itself.
    • Database connections, configuration, etc. needed by the handler are held by the application itself (e.g. a module-level static); the framework injects no extra parameters implicitly.
    • Two annotations in the same program declaring the same (method, path) are a compile error.
    • Registration order: annotated routes first, then the routes passed explicitly to http.router. Hence annotations take precedence when they duplicate explicit routes; the http.static wildcard generated by /* must be placed in explicit routes, otherwise it would shadow annotated routes.
    • Explicit route tables (http.get(path, handler) etc.) remain fully usable; without annotations, behavior is as before. The two approaches can be mixed.
    • When there are no explicit routes, pass an empty list: let extra: vec<http.route> = []; http.serve(8080, http.router(extra));.
    • The bind address defaults to 127.0.0.1 (the development default, reachable only from the local machine); rip run --host H / rip dev --host H can change it to 0.0.0.0, a local IP, or a domain name resolvable on the local machine; the startup log prints the actually configured address.

    11.2.2 HTTPS / TLS

    http.serve supports both plaintext HTTP and HTTPS; TLS is injected by the CLI and never written into Rip source:

    rip run main.rp --cert server.pem --key server.key --port 443
    • --cert is the PEM certificate chain (it may contain several certificates, the first being the site certificate); --key is the corresponding PEM private key (PKCS#8 or PKCS#1).
    • Both must be given together; when only one is given, http.serve reports the runtime error HTTPS requires both --cert and --key.
    • Once enabled, the startup log becomes https://, while the port, routes, static assets, and upload logic of http.serve remain completely unchanged.
    • Certificates and private keys are read only from the CLI and do not take part in rip build packaging; at deployment time place the PEMs at the specified paths on the target machine and point to them with --cert / --key.
    • TLS versions are negotiated by the runtime (TLS 1.2 / 1.3); client certificates are not verified (no mTLS).

    11.5 Scheduled Tasks and Concurrency (std/task + std/sync)

    Rip's concurrency model is thread-level isolation: each task runs in its own thread with its own interpreter state, and threads share no Rip variables, nor vec / map / ary.

    Scheduled tasks are declared with annotations and scheduled automatically when the program starts:

    #[interval("1m")]
func session_cleanup() -> void {
    // runs once per minute
}

#[interval("500ms")]
func poll_queue() -> void {
    // every 500 milliseconds
}

    Rules:

    • #[interval("...")] can only be attached to a module-level parameterless func; parameters, an unknown attribute name, or an illegal interval are all compile errors.
    • Interval format: a positive integer + ms (milliseconds) / s / m / h / d, e.g. "100ms", "30s", "5m", "1h", "1d"; it must be greater than 0.
    • Startup order: all scheduled tasks start before main begins executing; once main returns the process ends and the tasks terminate with it. A long-running service blocks http.serve in main, so tasks keep running.
    • The first execution of a task happens one interval later; it does not run immediately at startup.
    • An error inside a task does not terminate the process; it only prints [task] function name:line: error: ....

    One-off background tasks use std/task:

    use std::task;

task.spawn("send_report") -> bool        // runs a parameterless function asynchronously and returns immediately whether it started
task.sleep(milliseconds: int) -> void            // puts the current thread to sleep

    Async functions (async func / await):

    async func load(id: int) -> user {
    // executes in an independent runtime
    return fetch_user(id);
}

func handle(id: int) -> void {
    // start several tasks first and then wait as needed: the tasks truly run in parallel.
    let a: task<user> = load(1);
    let b: task<user> = load(2);
    let first: user = await a;
    let second: user = await b;
    print(first.name + second.name);
}
    • async can modify only module-level free functions; methods, main, and functions with attributes (route / interval / test) cannot be async.
    • Calling an async function hands the task to the scheduler immediately and returns task<T>; T is that function's return type. The task starts running at the call site and is not deferred until await.
    • await accepts only task<T> and returns T; using it on a non-task value is a compile error. A given task can be await only once (the ownership check blocks the second attempt).
    • A task that is not await still runs in the background and its result is discarded; always await when the result is needed.
    • A task function executes in an independent runtime: it cannot see the caller's local variables, module-level static, or closures, and can interact only through parameters, return values, and external resources such as databases / files / std/sync.
    • Parameters and return values are copied across threads; func / closures and task cannot cross task boundaries (a compile-time or runtime error is reported).
    • await on a failed task re-throws the original error (including the function stack) to the caller, consistent with synchronous calls.
    • The scheduler is a process-level bounded queue plus fixed worker threads (4× CPU cores, 8..=64); when the queue is full, work runs directly on the calling thread, providing backpressure. await first waits for a completion notification (about 200µs) so the task can finish in parallel on a scheduler thread; only if it is still unfinished at timeout does it opportunistically execute tasks in the queue, so nested await never deadlocks from worker exhaustion.
    • Task threads reuse an already-initialized runtime: before each task it clears globals, borrowed database / Redis connections, network handles, defer stacks, and the request context, then reinitializes module-level variables, giving the same isolation semantics as creating a new runtime while saving the runtime construction cost.
    • The debugger tracks only the thread that created the task; task threads run independently and do not hit breakpoints set by the caller.
    use std::time;

async func nap(ms: int) -> int {
    time.sleep(ms);
    return ms;
}

func main() -> void {
    let start: int = time.timestamp_ms();
    let a: task<int> = nap(400);
    let b: task<int> = nap(400);
    let total: int = await a + await b;
    // parallel execution: total time about 400ms, instead of the serial 800ms.
    print(total);
    print(time.timestamp_ms() - start);
}

    11.5.1 Cross-thread Sharing (std/sync)

    Rip values (vec / map / ary / closures) use single-thread reference counting and cannot cross threads. Shared cross-thread state uses process-level named primitives:

    use std::sync;

sync.mutex(name: string) -> sync.mutex
sync.atomic(name: string, initial: int) -> sync.atomic
sync.channel(name: string, capacity: int) -> sync.channel
sync.exists(name: string) -> bool
sync.remove(name: string) -> bool

    Rules:

    • Shared by name: within one process, the same name yields the same object, visible to HTTP worker threads, parallel branches, task.spawn, and #[interval].
    • Names must be fixed constants; do not concatenate request parameters into them (the registry is permanent by name, so dynamic names would grow without bound).
    • The same name cannot change type: creating it as a mutex and later using it as a channel reports a runtime error.
    • Handles are ordinary values and can be placed in vec / map / ary; calling their methods needs no let mut (they are process-level shared objects internally).
    • sync.remove is called only when no other thread is using that name (e.g. test teardown); after removal, the same name creates a new object while old handles still point to the old one.

    Mutex:

    mutex.lock() -> void
mutex.try_lock() -> bool
mutex.lock_timeout(ms: int) -> bool
mutex.unlock() -> void
mutex.is_locked() -> bool
mutex.name() -> string
    • lock blocks until acquired; try_lock returns immediately; lock_timeout waits at most ms.
    • The owner is not recorded, so any thread can unlock. Inside a critical section, defer is recommended for release:
    let mutex: sync.mutex = sync.mutex("report_lock");

func write_report(text: string) -> result<void, string> {
    mutex.lock();
    defer mutex.unlock();     // early return; released even on error
    fs.write_file("report.txt", text)?;
    return ok;
}

    Atomic integers:

    atomic.load() -> int
atomic.store(v: int) -> void
atomic.add(v: int) -> int      // returns the old value before the addition
atomic.sub(v: int) -> int      // returns the old value before the subtraction
atomic.swap(v: int) -> int     // returns the old value
atomic.compare_swap(old: int, new: int) -> bool
atomic.name() -> string
    • All are SeqCst atomic operations, suitable for counters, ID allocation, and task completion flags.
    • initial takes effect only on the first creation; later calls with the same name do not reset it.

    Channels:

    channel.send(value: any) -> void
channel.try_send(value: any) -> bool
channel.send_timeout(value: any, ms: int) -> bool
channel.recv() -> option<any>
channel.try_recv() -> option<any>

    • Bounded queue: capacity 1..1000000; when full, send blocks, try_send returns false, and send_timeout waits at most ms.
    • recv blocks until a value is available or the channel closes; try_recv returns immediately; recv_timeout waits at most ms.
    • After closing: queued values can still be read and then recv immediately returns none; send errors, and try_send / send_timeout return false.
    • A channel transfers a deep copy of the value (preserving int / i8... u64, the option / result / ary class names, and map key types), not a shared reference; function values cannot go through a channel.
    • option<any> is narrowed with .as_int() / .as_string() etc., consistent with the json.decode convention.
    // producer: a background task
func worker() -> void {
    let jobs: sync.channel = sync.channel("jobs", 64);
    let done: sync.atomic = sync.atomic("jobs_done", 0);
    jobs.send(42);
    done.add(1);
}

// consumer: the main thread polls with a timeout and is never blocked forever
task.spawn("worker");
let jobs: sync.channel = sync.channel("jobs", 64);
match jobs.recv_timeout(1000) {
    some(value) => { dev.log(value.as_int().unwrap_or(0).to_string()); }
    none => { dev.log("1 seconds with no message"); }
}

    Timeouts and cancellation:

    • All blocking operations (lock / lock_timeout / send / send_timeout / recv / recv_timeout) check the HTTP handler's deadline every 20ms; when a request times out it is interrupted immediately and 504 is returned, so a worker thread never hangs while waiting for a lock or channel.
    • Background tasks have no deadline; use *_timeout variants or try_* to control them yourself and avoid blocking forever.
    • Threads still do not share Rip variables; the only things to share are std/sync primitives and process-level external resources (caches, queues, Redis, databases).

    Combined with parallel, note the following: each statement of parallel is an independent branch and cannot see outer local variables; get handles inside a branch with same-named primitives to aggregate results.

    parallel {
    sync.atomic("jobs_done", 0).add(1);
    sync.atomic("jobs_done", 0).add(1);
}
let done: sync.atomic = sync.atomic("jobs_done", 0);
// done.load() == 2

    Multi-instance deployment: scheduled tasks start on every machine and run repeatedly by default. With [cluster] redis + task_lock = true configured, a Redis lease is used to elect a leader before each trigger, and only the instance that wins rip:task:<function name> executes; see 11.11 for details.

    Rules:

    • Digest functions return lowercase hexadecimal strings; base64_* uses standard Base64 (with = padding).
    • base64_decode / hex_decode return err("invalid ... input") on invalid input rather than terminating the process.
    • random_hex(n) returns a hex string of n bytes of cryptographic randomness (length 2n); n must be within 1..=1024, and out-of-range values return err(...).
    • password_hash returns ript$iterations$salt$digest: PBKDF2-HMAC-SHA256 (210000 iterations) with a 16-byte random salt, so the same password yields a different result each time; the iteration count is embedded in the hash string, so raising it later does not affect verification of old data.
    • password_verify(password, hashed) reads the iteration count and salt from the string, recomputes, and compares in constant time; it accepts only the ript$ format, and old formats, invalid strings, abnormal iteration counts, or password mismatches all return false without throwing.
    • Store only the result of password_hash in password fields, and always verify with password_verify; do not concatenate sha256 yourself for comparison. In production use the release build of rip (cargo build --release): the debug runtime is unoptimized and takes seconds per hash, while the release build takes about 100–150ms.
    • aes_encrypt / aes_decrypt use AES-256-GCM: any string key is derived to 32 bytes via SHA-256, and the output is base64(12 random bytes nonce || ciphertext || 16 byte auth tag); decryption returns err(...) when the key is wrong or the ciphertext has been tampered with.
    • rsa_*: rsa_sign / rsa_verify use RSA PKCS#1 v1.5 signatures (the digest is fixed to SHA-256 internally, and the result is Base64); rsa_encrypt / rsa_decrypt use RSA-OAEP (SHA-256) and do not adopt PKCS#1 v1.5 encryption, which is vulnerable to Bleichenbacher attacks (old v1.5 ciphertexts cannot be decrypted by the current runtime). rsa_generate(bits) generates a bits -bit key pair (1024..=8192 and a multiple of 8) and returns private_key_pem (PKCS#8) and public_key_pem (SPKI).
    • aes_encrypt / derive_key derive keys directly with SHA-256 and are only suitable for high-entropy keys (such as random_hex(32) or keys injected via configuration); with a passphrase the key must first go through password_hash/KDF, never passing a weak passphrase directly.
    • Private / public key PEMs accept both PKCS#8 / PKCS#1 (public keys SPKI / PKCS#1), for interoperability with tools such as OpenSSL.
    • This package handles only data encryption and signing; HTTPS certificate loading and TLS handshakes are provided by the runtime through --cert / --key (see 11.2.2), and Rip source never touches TLS details beyond the private key.

    11.10 WebSocket (std/ws)

    use std::ws;

ws.serve(port: int, handler: func(ws.conn) -> void) -> void

ws.send(conn: ws.conn, text: string) -> result<int, string>

ws.ping(conn: ws.conn) -> result<bool, string>

    Rules:

    • ws.serve listens on 127.0.0.1 (or --host) and completes the handshake, calling handler once per connection; the connection is closed after the handler returns, and the handler uses ws.recv / ws.send for bidirectional communication.
    • Handshake security: the handshake read/write timeout is 10 seconds, so slow connections do not occupy the service; requests carrying Origin (initiated by browsers) where Origin and Host are not the same origin are rejected with 403, preventing cross-site WebSocket hijacking; non-browser clients (without Origin) are unaffected.
    • The client uses ws.connect(url, timeout_ms) and supports ws:// and wss://: wss:// performs the TLS handshake with rustls + the system root certificate store (validating the chain and host name), with port 443 by default (ws:// defaults to 80); the server-side ws.serve still listens only in plaintext, and HTTPS sites are terminated by the TLS configuration of [server].
    • Only text frames (UTF-8) are handled; binary frames are decoded as text; ping is answered with pong automatically, and after close is received, recv returns err("connection closed").
    • A single frame is limited to 16 MiB; ws.conn is an opaque handle, and operating on it after closing returns err(...).

    Rules:

    • The URL accepts only redis:// and rediss://, in the form redis://[user:password@]host[:port][/db]; rediss:// validates TLS with system root certificates.
    • A connection belongs to the current interpreter (thread) and is not shared across threads; connection timeout is 5 seconds and the read/write timeout is 10 seconds, returning err(...) on timeout instead of blocking the request thread.
    • redis.connect transparently reuses a process-level pool of idle connections keyed by URL: when connecting to the same URL again, an idle connection is lent out first (liveness is checked with PING before lending, and expired or closed connections are discarded and the search continues); clean connections are returned to the pool on conn.close() or when the task ends, while connections with failed reads/writes or unread replies are discarded. Each URL caches at most 8 idle connections, and ones idle for more than 300 seconds are evicted on the next lend; lending/returning never blocks and the total number of connections lent out is unlimited.
    • redis.lock acquires a lease with SET key token NX PX ttl: it returns some(token) on success and none if someone else holds it; redis.unlock compares the token in Lua before deleting, avoiding accidental deletion of another holder's lease. Leases expire automatically, so a crashed holder does not deadlock forever.
    • redis.rate_limit is fixed-window counting: the first limit requests in a window return true, and excess ones return false.
    • Cluster scheduled tasks: with the rip.toml of [cluster] redis giving the address and task_lock = true enabling leader election, each #[interval] task acquires a rip:task:<function name> lease before every trigger, and only the winning instance executes. The lease lasts twice the interval (minimum 10 seconds); when Redis is unavailable it degrades to local execution so that tasks are not interrupted.
    • Sessions, caches, distributed locks, and cluster rate limiting are all built on this foundation; the runtime keeps no cross-instance state inside the local process.

    11.13 Observability (Tracing, Logging, Metrics)

    Tracing: OTLP/HTTP JSON export is enabled once [server] otlp_endpoint is configured.

    • One server span per HTTP request: the name is method route pattern, and attributes include http.method / http.target / http.route / http.status_code / http.client_ip / duration_ms; 5xx is recorded as an error status.
    • Database execute / query are attached as child spans under the current request span; the SSE span covers the entire push process.
    • The trace id and span id of an inbound traceparent are reused (distributed traces stay unbroken); a new trace id is generated when there is no upstream; outbound http.fetch / http.download automatically add a new traceparent.
    • Sampling is determined deterministically by trace id, so all spans of the same trace get the same decision; the queue limit is 4096, and when full the oldest are dropped and counted in rip_trace_spans_dropped_total.
    • A failed export puts the whole batch back into the queue for retry; when the Collector is unavailable for a long time, the queue limit still applies and memory does not blow up.

    Logging: the std/log format of json automatically includes request_id and trace_id in a request context, aligning directly with tracing.

    • log.set_file(path) followed by log.set_rotate(max_bytes, keep) enables rotation: when a single file exceeds max_bytes, it is renamed to .1, .2... in turn, keeping keep copies, and the original file is reopened to continue appending.
    • Rotation state belongs to the current interpreter; each HTTP worker thread holds its own, and when writing to the same path each thread rotates independently (use a Collector / log agent when single-file centralized collection is needed).
    • The access log ([server] access_log, enabled by default) is appended to memory only by request threads, and a background thread writes whole batches to stdout every 100ms: a slow stdout does not stall requests; the buffer limit is 16MB, beyond which new logs are dropped and counted in rip_access_log_dropped_total.

    Metrics: [server] metrics_path exposes HTTP, rate limiting, database, cache, and trace counters; naming is described in 11.12 and 10.13.

    Engineering tools:

    • rip test --coverage [--coverage-min N]: statement-line coverage; both the interpreter and bytecode execution paths are instrumented, and the bytecode gains no extra instructions when it is off.

    • rip fmt [file|dir] [--check] [--stdout]: unifies indentation and blank lines; --check is suitable as a CI gate.

    • Attachment content: content_base64 takes precedence when non-empty, otherwise path is read; filename is mandatory.
    • Headers are encoded per RFC 2047 and the body is UTF-8; timeout_ms limits a single socket operation, and 0 means no timeout.
    • mail.send is a blocking call: inside an HTTP handler, run it in a background function via task.spawn.

    11.15 Reflection and Dynamic Dispatch (std/reflect)

    Static typing is preferred. Reflection is used only for logging, serialization, plugin bridging, and other cases that genuinely need to read struct fields or call methods by name at runtime.

    reflect.type_name(value: any) -> string
reflect.kind(value: any) -> string
reflect.fields(value: any) -> vec<string>
reflect.has(value: any, name: string) -> bool
reflect.get(value: any, name: string) -> option<any>
reflect.variant(value: any) -> option<string>
reflect.invoke(value: any, method: string, args: vec<any>) -> result<any, string>
reflect.is(value: any, name: string) -> bool
    • type_name returns the concrete type name: for structs and enums it is the declared name (e.g. user, status), otherwise the built-in name (int, string, vec, map, option, result, func, none, null).
    • kind returns the category name: structs and enums are uniformly "struct", and the rest are the same as type_name.
    • fields is the list of visible field names: structs in declaration order (excluding the internal #variant), map with string keys, and vec with "0", "1"....
    • get supports struct fields, map string keys, and vec numeric indices; returns none when absent. has is the boolean form of get.
    • variant returns the variant name only for enum values and none for everything else; fieldless variants also apply.
    • invoke calls a method with the given name (the same semantics as . calls) and returns ok(value) on success; a missing method, mismatched argument types, or a runtime error all return err(message) without terminating the program.
    • is determines whether type_name or kind equals the given name, used by plugins to dispatch by type.
    • Reflection does not change type checking: parameter positions accept any value (the in-library signature is any) and return values are any; extracting values still requires explicit conversion (see Section 12); user code does not need to and should not write any.
    use std::reflect;

type user = [name: string, age: int];

func describe(u: user) -> string {
    return reflect.type_name(u) + " " + reflect.fields(u).to_string();
}

func trim_text(text: string) -> string {
    match reflect.invoke(text, "trim", []) {
        ok(v) => return v.as_string().unwrap_or(""),
        err(_) => return "",
    }
}

    12. any Type Rules

    • any may appear only in map<string, any> value types and at JSON decoding boundaries (json.decode / req.json).
    • Extracting a value from any requires explicit conversion: .as_string() / .as_int() / .as_float() / .as_bool() / .as_vec() / .as_map(), returning option<T>.
    • any does not participate in compile-time type checking and loses static safety; it is an explicit escape hatch.
    • Except for map<string, any>, in every other position any is forbidden.

    14. Compilation Pipeline

    source .rp
  ↓
[Lexer] → Token stream
  ↓
[Parser] → AST
  ↓
[Type Checker] → typed AST, reports a type error
  ↓
[Ownership Checker] → borrow/lifetime/Send-Sync check, insert drop/move/borrow point
  ↓
┌─────────────────────┬─────────────────────┐
│ interpreter mode             │ AOT pattern             │
│ AST → Bytecode       │ AST → LLVM IR        │
│ VM execution               │ LLVM → ELF/EXE       │
└─────────────────────┴─────────────────────┘

    Key constraint: interpreter mode must also run the full front-end checks first (types + ownership); checking while running is not allowed. The check results are passed as intermediate information to both back ends.

    Current implementation: interpreter mode attempts to compile each function into stack bytecode (scalar subset only); functions that cannot be compiled fall back to the tree-walking interpreter as a whole, and both share type-check results and operation/call implementations. RIP_NO_VM=1 forces fully interpreted execution, for behavior comparison. AOT offers two paths: rip build --native translates the scalar int subset into Rust and compiles it with rustc -O (fully standalone, with no runtime support library); rip build --aot translates the full syntax into Rust and statically links rp-runtime, so the artifact contains neither source code nor a language front end.

    16. Implementation Hard Constraints

    1. Exactly one spelling: one semantics allows only one syntax; no aliases, sugar, or second spellings.
    2. No inference: all types are explicit; the only exceptions are for / match destructuring.
    3. Check before execute in interpreter mode: checking while running is not allowed.
    4. Reference counting + cycle collection: containers are freed immediately with Rc, and cycles where closures and containers point at each other are cleaned by the runtime cycle collector; no full tracing GC is provided. The heap limit is controlled by [server] max_heap_mb, and an over-limit request ends with a runtime error.
    5. No unsafe exposure: no raw pointers and no unsafe at the user level.
    6. No eval: executing string code at runtime is forbidden.
    7. ary fields are closed: fields cannot be added at runtime.
    8. Subscripts forbidden: all access goes through the dot.
    9. HTTP format is decided by return : choose exactly one of body / json / sse; the framework does not enforce it.
    10. Rust packages are called only through Rip syntax: no Rust-specific syntax is exposed, and the type mapping is fixed.
    11. Naming convention check: violations produce a warning; --deny-warnings escalates them to errors.
    12. Shadowing forbidden: variable names are unique within a scope.

    In a Nutshell

    Rip (rui, .rp, tool rip, manifest rip.toml) is a strongly typed, zero-inference, class-free, GC-free server/Web language with Rust ownership semantics and Go structure + PHP ease of use. Three data structures ary (fixed fields), vec (ordered indexed sequence), map (dynamic key-value dictionary); variables let / let mut / const / static, all types explicit, shadowing forbidden, naming snake_case (constants SCREAMING_SNAKE_CASE); integers int (= i64) / i8... i64 / u8... u64; parameter modifiers read / write, Copy types copy and Move types transfer by default; the HTTP response format is decided by return , choosing one of body / json / sse ; Rust packages are introduced through use rust::xxx; and are always called with Rip syntax. The implementation is Lexer → Parser → type check → ownership check → dual back ends (bytecode VM / LLVM AOT), with interpretation and compilation sharing the same front-end checks; completion is when all 12 items of the Part IV checklist pass one by one.
